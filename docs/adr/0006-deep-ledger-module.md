# 深 Ledger 模块与统一装配

## 状态

Accepted

## 背景

原有账目实现将一次用户操作拆分为 Store、Service、Repository 和 `Database` 多层转发。层间接口暴露了持久化细节，依赖在多个位置自行创建，列表和汇总也可能来自不同读取时刻。这样的浅层结构增加了调用路径和测试替身数量，却没有隐藏金额、日期、软删除和一致性等关键复杂度。

账目 MVP 只有一个核心业务边界，适合由一个对外接口小、内部实现深的模块承担规则和持久化协调。

## 决策

- 使用一个 `Ledger` 深模块作为账目功能的唯一业务接口，提供快照读取以及新增、编辑、删除操作。
- `Ledger` 模块内部拥有金额解析、日期校验、软删除、汇总、SQLite 查询和事务边界；不向 UI 暴露 SQL、数据库行或仓储实现。
- `snapshot()` 在同一个一致读取中返回常规可见的条目列表和汇总。
- 应用 composition root 创建 SQLite 连接、时钟和标识生成器，并将已装配的 `Ledger` 提供给 UI。
- UI 只依赖 `Ledger` 接口，不创建 Service、Repository 或数据库对象。
- 不使用浅层 Store/Service/Repository/Database 链，也不为未出现的存储替换需求设计假想 port。

本 ADR 替代 [按功能组织应用模块](0003-feature-oriented-modules.md)。

## 后果

- 金额、日期、删除可见性和快照一致性在一个模块内定义和验证，减少跨层重复。
- 测试可以用真实 SQLite 验证模块行为；UI 测试只替换完整 `Ledger` 接口，而非复制底层 SQL 语义。
- 依赖生命周期和平台装配集中在 composition root，避免页面和 hook 隐式创建多套依赖。
- 新增功能只有在形成独立业务边界时才创建新模块；不得为了目录对称性重新拆出纯转发层。
