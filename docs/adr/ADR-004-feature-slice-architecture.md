# ADR-004: Feature-Slice 架构模式

日期：2026-04-05
状态：已采纳

## 背景

记账应用已完成第一个功能模块（账目 CRUD），即将开始添加更多功能模块（统计报表、分类管理、账户管理、预算管理等）。在继续开发之前，需要确定代码组织架构，避免后期代码混乱难以维护。

### 面临的问题

1. **代码组织混乱**：现有代码按技术类型分散存放，功能增多后难以定位
2. **模块边界不清**：没有明确的模块边界，容易产生循环依赖
3. **状态管理分散**：各组件独立管理状态，数据流不清晰
4. **复用性差**：功能之间难以共享代码

### 候选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| 按类型分层 (MVC) | 简单直观 | 功能多了文件分散，维护困难 |
| Feature-Slice | 功能内聚，边界清晰 | 需要学习成本 |
| 领域驱动设计 (DDD) | 业务导向，适合大型项目 | 对小型项目过于复杂 |

## 决策

采用 **Feature-Slice 架构模式**，配合 **Zustand** 状态管理。

### 核心原则

1. **Feature 自包含**：每个功能模块包含该功能的所有层级代码
2. **单向依赖**：features 依赖 shared，features 之间不相互依赖
3. **公开 API**：每个 feature 通过 `index.ts` 导出公开接口
4. **状态隔离**：每个 feature 有独立的 Zustand store

### 目录结构

```
src/app/src/
├── features/                      # 功能模块 (核心)
│   ├── ledger/                    # 账目功能
│   │   ├── components/            # 账目相关组件
│   │   ├── screens/               # 页面
│   │   ├── hooks/                 # 业务 hooks
│   │   ├── stores/                # Zustand store
│   │   ├── services/              # 业务逻辑
│   │   ├── repositories/          # 数据访问
│   │   ├── types/                 # 类型定义
│   │   └── index.ts               # 公开 API
│   │
│   ├── statistics/                # 统计报表 (未来)
│   ├── categories/                # 分类管理 (未来)
│   ├── accounts/                  # 账户管理 (未来)
│   └── budget/                    # 预算管理 (未来)
│
├── shared/                        # 共享资源
│   ├── components/                # 通用组件
│   ├── hooks/                     # 通用 hooks
│   ├── stores/                    # 全局状态
│   ├── types/                     # 通用类型
│   ├── utils/                     # 工具函数
│   └── db/                        # 数据库抽象
│
├── navigation/                    # 路由配置
│   ├── AppNavigator.tsx           # 根导航
│   ├── features/                  # 各 feature 的路由配置
│   ├── routes.ts                  # 路由常量
│   └── types.ts                   # 路由类型定义
│
└── App.tsx                        # 应用入口
```

### 状态管理选择：Zustand

选择 Zustand 而非 Redux/Context 的理由：

| 特性 | Zustand | Redux | Context |
|------|---------|-------|---------|
| 学习曲线 | 低 | 高 | 低 |
| 代码量 | 少 | 多 | 中 |
| 性能 | 好 | 好 | 一般 |
| 调试工具 | 有 | 强大 | 无 |
| 适合规模 | 中小型 | 大型 | 小型 |

对于独立开发的记账应用，Zustand 在简单性和功能性之间取得了最佳平衡。

## 后果

### 正面影响

- **功能内聚**：相关代码集中在同一目录，易于查找和维护
- **边界清晰**：Feature 之间不相互依赖，降低耦合
- **扩展性强**：新增功能只需添加新 feature 目录
- **测试隔离**：每个 feature 可以独立测试
- **代码复用**：shared 层促进通用代码复用

### 负面影响

- **初期成本**：需要重构现有代码
- **目录嵌套**：目录层级较深
- **学习曲线**：新成员需要理解架构
